# 배포 사이트에 로그인 켜기 + 이메일 인증을 일부러 끈 판단

- 날짜: 2026-11-23
- 프로젝트: SceneWalk AI (4인 팀 캡스톤, 웹 3D 관광 맵). JM 담당: 로그인·역할·스탬프·쿠폰 API, DB(Supabase), 배포
- 사용 도구: Claude Code (Opus 5.5), Vercel, Render, Supabase Auth, GitHub API, curl
- 목표: 배포 사이트(Vercel)가 실제 서버(Render)·DB(Supabase)를 쓰도록 연결하고, 팀원이 역할별로 테스트할 계정 방식을 정한다.

## A. AI가 한 일
- Vercel 프로젝트 소유 확인: 내 Vercel 계정에는 팀 프로젝트가 없고, 팀 사이트는 다른 팀원 계정 소속임을 GitHub 커밋 상태의 Vercel 링크와 대시보드 404로 확인함 — 증거: GitHub `commits/main/statuses`의 `target_url`
- 환경변수 성격 판단: `VITE_API_URL`은 빌드 때 화면 코드에 그대로 들어가는 값이라 시크릿이 아니라 설정값이라고 설명함. 진짜 비밀 키는 Render 서버에만 둠 — 근거: `frontend/src/api/session.js:10`
- 적용 여부를 "말"이 아니라 결과물로 검증: 팀원이 "넣었다/업데이트됐다"고 한 뒤에도 배포된 JS 번들 이름과 내용을 직접 받아 서버 주소가 없음을 두 번 확인함(값만 저장하고 재배포 안 함 → Preview/Production 혼동 가능성 안내). 재배포 뒤 번들이 `index-Bwtf6bJx.js` → `index-BwBLCg5g.js`로 바뀌고 서버 주소가 들어간 것을 확인함
- 연결 확인: Render 서버가 배포 도메인에 CORS 허용(`OPTIONS` 204, `access-control-allow-origin` 일치), 사이트에 서버 모드 전용 로그인 상자(`UiRoot.jsx:41`)와 로그인 창이 뜨는 것을 확인함
- 인증 설정 조회: 공개 키로 Supabase Auth 설정을 조회해 이메일 인증이 꺼져 있음(`mailer_autoconfirm: true`)을 확인함
- 이메일 인증을 켜자는 요청에 반대 의견 제시: 무료 기본 메일 발송기는 조직 멤버에게만·시간당 몇 통만 보내서 시연 중 가입이 막힐 위험을 설명하고, 시연까지는 끄고 문서로 규칙을 지키는 대안을 권함
- 역할별 테스트 계정 설계: 공용 계정 대신 Gmail `+owner` 별칭으로 각자 계정 2개(관리자·사장님)를 갖게 하고, 가게 지정 SQL과 정리 SQL을 문서화함 — 증거: `docs/jm-admin-accounts.md`

## B. 사용자가 직접 한 일
- Vercel 프로젝트 주인(팀원)에게 환경변수 설정·재배포를 부탁하고, 빌드 상태를 확인받음
- Vercel 대시보드에 직접 로그인함(비밀번호 입력은 본인)

## C. AI 판단과 달리 사용자가 결정한 일
- 처음에는 이메일 인증을 켜서 실제 이메일로만 가입되게 하려 함 → 위험 설명을 듣고 시연(11/30)까지 끄기로 결정
- 공용 역할 계정이 아니라, 각자 가입 + 역할별 계정 방식으로 결정

## 결과와 배운 점
- 결과: 배포 사이트가 mock 모드(브라우저 저장) → 서버 모드(실제 DB 저장)로 바뀜. 로그인 없이 둘러보기, 스탬프 때만 로그인
- 배운 점
  - 환경변수는 "저장"과 "반영"이 다르다. 빌드 시점 값(`VITE_`)은 재배포해야 들어가고, 확인은 배포 결과물(번들)로 해야 한다
  - 보안 설정을 켜는 것이 늘 정답은 아니다. 이메일 인증은 메일 발송 인프라(SMTP)까지 있어야 동작하고, 없으면 가용성(가입 자체)이 깨진다
- 남은 일: 실제 로그인 후 다른 기기에서 스탬프가 보이는지 확인, 시연 뒤 무료 SMTP 연결 후 이메일 인증 켜기 검토

## A. AI가 한 일
- **원인 찾기 (역할이 안 바뀌어 보임)**: DB를 직접 조회해 두 계정이 `admin`으로 저장돼 있음을 먼저 확인 → 문제는 DB가 아니라 화면이라고 좁힘. 화면이 로그인 응답을 localStorage에 저장해 두고, 토큰 갱신(`/auth/refresh`) 때도 역할을 다시 받지 않는 구조임을 코드에서 찾음 — 근거: `frontend/src/api/session.js` (수정 전 `/me` 호출 없음)
- **닉네임 API 설계**: `PATCH /me`는 이름만 받고 역할·가게는 보내도 무시. DB 트리거 `guard_profile_update`가 한 번 더 막으므로 두 겹 방어. 이름 변경은 감사 로그에 남기지 않음(역할·가게 변경만 기록하는 기존 설계 유지) — 증거: `server/src/app.js` `PATCH /me`, 테스트 4개
- **관리자 통계 DB 함수**: 스탬프·쿠폰 테이블은 RLS가 "내 것만"이라 관리자도 전체를 못 셈 → `security definer` 함수로 모으되,
  1. 함수 첫 줄에서 관리자인지 직접 검사(아니면 `NOT_ADMIN`)
  2. 누가 찍었는지 같은 개인 정보 없이 **집계 숫자만** 반환
  3. 실행 권한은 로그인한 사람만(`anon` 회수)
  — 증거: `supabase/migrations/20261126120000_jm_admin_stats.sql`
- **실제 DB에서 권한 검증**: SQL Editor에서 계정을 바꿔 가며(`request.jwt.claims` + `role authenticated`) 실행 → 관리자는 실제 숫자, 순례객은 `NOT_ADMIN`으로 거절되는 것을 확인
- **배포 확인을 결과물로**: 합친 뒤 Render 응답 코드(`/me` PATCH, `/admin/stats` 404 → 401)와 Vercel 번들 안의 코드로 새 버전이 올라갔는지 확인
- **로딩이 느려진 원인 측정**: 배포 사이트에서 로딩 5.6초 중 약 3초가 JS 실행(6.4MB 한 파일, 안에 WebAssembly 약 2MB × 2)임을 측정. 오늘 로그인 작업 전후 번들 크기는 같아서 원인이 아님을 확인. 고치는 건 성능 담당(성근)·로딩 담당(병관) 영역이라 측정값만 공유
- **사람 실수 짚기**: 병관님 계정이라고 넣은 이메일이 실제로는 성근님 계정임을 DB 닉네임으로 확인 (병관님 계정은 이미 admin이었음)

## B. 사용자가 직접 한 일

- 배포 사이트에서 관리자 표시·관리자 화면이 열리는지 직접 확인

## C. AI 판단과 달리 사용자가 결정한 일
- 처음 문서에는 "공용 계정을 쓰지 않는다"고 적었지만, **사장님 역할은 공용 계정 1개를 팀이 같이 쓰기로** 결정함. (AI가 알린 위험: 같은 이메일 15분 5번 실패 시 모두 잠김, 감사 로그가 한 사람으로 찍힘)
- 관리자 화면은 성근님 담당이지만, 서버·DB 부분은 성근님 확인을 기다리지 않고 지민이 만들기로 결정 (PR 설명에 성근님 파일 2줄 수정을 명시)

## 결과와 배운 점
- 결과: 배포 사이트에서 관리자 4명이 관리자 화면에 실제 숫자를 볼 수 있음. 서버 테스트 48개 통과
- 배운 점
  - **"DB에 저장됨"과 "사용자가 보는 값"은 다를 수 있다.** 권한 정보를 클라이언트에 캐시하면, 권한이 바뀌었을 때 언제 다시 읽을지까지 설계해야 한다
  - **RLS를 우회하는 함수는 문을 하나 더 여는 것**이라, 함수 안에서 권한 검사·내보내는 값(집계만)·실행 권한 세 가지를 같이 막아야 한다
  - 문제가 생기면 화면 → 서버 → DB 순서로 "어디까지는 맞는지"를 확인해서 범위를 좁힌다
