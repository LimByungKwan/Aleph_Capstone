# 물려받은 PC에 남은 이전 사용자 GitHub 로그인 정리

- 날짜: 2026-11-18
- 프로젝트: SceneWalk AI (4인 팀 캡스톤, 팀장 소유 GitHub 저장소에서 협업)
- 사용 도구: Claude Code (Opus 5.5), Git, GitHub CLI(`gh`), Windows 자격 증명 관리자, VS Code
- 목표: 공용 PC에서 팀 저장소에 올린 커밋이 이전 사용자 이름으로 기록된 원인을 찾고, 앞으로의 커밋과 푸시가 확실히 내 계정으로 올라가게 한다.

> 공개용 주의: 이전 사용자의 계정명과 이메일은 개인정보이므로 이 기록에서 "이전 사용자 계정"으로만 적는다.

## A. AI가 한 일
- 원인 구분 설명: 커밋 작성자는 `git config`의 `user.name`·`user.email`이 정하고, 푸시와 PR 작성자는 로그인 토큰(자격 증명 관리자, `gh` 로그인, 앱 로그인)이 정한다는 점을 나눠 설명함
- 숨은 원인 발견: 자격 증명 관리자를 정리한 뒤에도, git이 푸시할 때 `gh`에서 비밀번호를 받아오도록(`gh auth git-credential`) 설정되어 있었고, 그 `gh`에 이전 사용자 계정이 로그인되어 있던 것을 찾음 — 증거: `~/.gitconfig`, `gh auth status`(대화 기록)
- 이전 사용자 로그아웃: 이전 사용자 계정을 `gh`에서 로그아웃시킴(사용자 요청)
- 터미널 환경 차이 분석: VS Code bash(MSYS2 UCRT64), Windows PowerShell, Claude 실행 환경이 `gh` 설정을 서로 다른 곳에서 읽어 로그인 상태가 다르게 보였음을 확인함. 처음부터 기준 터미널을 하나로 정하지 않아 여러 번 오간 점은 AI 진행 방식의 실수였음
- 로컬 Claude 설정 점검: 전역 지침과 스킬 캐시, 대화 기록에 이전 사용자 흔적이 있음을 찾아 알리고, 사용자 확인 후 휴지통으로 옮김(영구 삭제 아님)
- 기록 처리 판단 제시: 팀 저장소의 main은 커밋 기록을 다시 쓰지(강제 푸시) 말고 그대로 둔 뒤 팀장에게 알리는 쪽을 권함
- 오늘 푸시 전 재확인: 저장소의 커밋 작성자가 본인 이름인지 확인한 뒤 SG 브랜치에 푸시하고, GitHub API로 새 커밋(`e5fa29c`)이 본인 계정에 연결된 것을 확인함 — 증거: GitHub commits API `author login`, `committer login` 모두 본인 계정

## B. 사용자가 직접 한 일
- 문제 발견: PR 기록에 이전 사용자 이름이 찍힌 것을 발견하고 원인 확인을 요청함
- git 작성자 설정: 전역 `user.name`·`user.email`을 본인 것으로 설정하고, 저장소 안에서 `git config user.email`과 `git log`로 확인함 — 증거: 병합 커밋 `d3c4066`이 본인 이름으로 기록됨
- 자격 증명 관리자 정리: GitHub 자격 증명이 두 개(본인, 이전 사용자) 있던 것을 확인하고 본인 것만 남김
- 본인 계정 로그인: PowerShell에서 `gh auth login`을 직접 실행해 브라우저 승인으로 본인 계정에 로그인함(토큰과 일회용 코드는 채팅에 공유하지 않음)
- 이전 사용자 정체 확인: 이전 사용자가 수료 후 취업해서 떠난 이전 수강생이라는 사실을 확인해 알려 줌
- 팀장에게 보고: 이전 사용자 계정이 저장소 Collaborator(협업자)에 남아 있는지 확인을 요청했고, 없다는 답을 받음
- 로컬 Claude 설정 정리: 이전 사용자의 스킬 대부분을 직접 지우고, 전역 지침을 본인에 맞게 다시 씀
- 승인: 팀 저장소의 기존 커밋 기록은 다시 쓰지 않고 그대로 두기로 함

## 결과와 배운 점
- 결과
  - 커밋 작성자: 본인 이름으로 기록됨 (`d3c4066`, `e5fa29c`)
  - 푸시와 계정 연결: 2026-11-18 SG 브랜치 푸시에서 새 커밋 `e5fa29c`가 GitHub의 본인 계정에 연결된 것을 확인함
  - 이전 기록: 11/17 SG 브랜치 커밋 2개는 작성자 이름만 이전 사용자로 남았고, GitHub 이벤트 기록상 그 푸시 자체는 본인 계정으로 됨. 기록은 다시 쓰지 않고 그대로 둠
  - 이전 사용자 계정: `gh` 로그아웃, 자격 증명 삭제, 저장소 Collaborator에 없음 확인
- 배운 점
  - "누가 커밋했나"와 "누가 푸시했나"는 다른 설정이 정한다. 하나만 고치면 문제가 남는다.
  - 자격 증명 관리자만 보면 안 된다. git이 실제로 어떤 credential helper(인증 정보를 넘겨주는 도구)를 쓰는지 `~/.gitconfig`에서 확인해야 한다.
  - 같은 PC라도 터미널 환경마다 설정 저장 위치가 다를 수 있다. git 작업은 터미널 하나로 통일한다.
  - 공용 저장소의 기록은 고칠 수 있어도, 팀원 전체 기록이 어긋나는 강제 푸시보다 그대로 두고 알리는 쪽이 낫다.
- 재발 방지 체크리스트 (새 PC를 받았을 때)
  1. `git config --global user.name` / `user.email`
  2. `git config --get-all credential.helper`와 `credential.https://github.com.helper`
  3. `gh auth status` (git이 쓰는 `gh` 경로 기준)
  4. Windows 자격 증명 관리자의 `git:https://github.com` 항목
  5. VS Code, Copilot 등 앱별 GitHub 로그인
  6. 첫 푸시 후 GitHub 커밋 목록에서 본인 프로필로 연결됐는지 확인
