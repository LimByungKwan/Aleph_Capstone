# 썬그레이 오디션 MVP 1단계: 뼈대 (기준 멜로디 · 장치 감지 · 녹음 업로드)

- 날짜: 2026-11-23
- 프로젝트: SceneWalk (Aleph Capstone) — SG 담당
- 사용 도구: Claude Code (Opus 5.5), FastAPI, Python 3.13, pytest, React(Vite), MediaRecorder·Web Audio API
- 목표: 노래 녹음을 받아 기준 멜로디와 비교할 수 있도록 입력 데이터·장치 분기·업로드 경로를 먼저 세운다.

## A. AI가 한 일
- 설계 질문과 반례 제시: 늦게 시작하면 모든 음이 밀림, URL을 클라이언트가 보내면 가짜 기준 멜로디·SSRF 위험, 곡 id 경로 조작(`../../admin`), HTTPS가 아니면 `mediaDevices` 없음, 정상 프론트 밖의 거대 파일·가짜 wav
- 사실 확인: 브라우저별 녹음 형식(webm/mp4)과 librosa 읽기 제약, `python-multipart` 누락, 기존 `allow_request`가 코스 추천과 횟수를 같이 셈
- 구현 (사용자 위임)
  - 기준 멜로디 `frontend/public/audition/sungray-01.json` (12음, 9초, 직접 만든 멜로디)
  - 장치 감지 `frontend/src/components/sg/micMode.js` — 5가지 분기를 가짜 navigator로 확인
  - 업로드 API `ai/app/audition.py` + 테스트 7개 `ai/tests/test_audition.py`
  - 녹음·wav 변환·업로드 `frontend/src/components/sg/auditionTake.js`
  - 공용 파일: `ai/app/main.py` 2줄, `ai/requirements.txt` 1줄, `.claude/launch.json` 설정 1개
- 디버깅: 정상 업로드가 400이 나던 원인 찾음. `request.form()`은 Starlette `UploadFile`을 주는데 FastAPI `UploadFile`(하위 클래스)로 `isinstance` 검사
- 설계 변경 1건: 곡 id는 폼 안에 있어서, 크기 검사(`Content-Length`, 413)를 곡 id 검사보다 앞으로 옮김

## B. 사용자가 직접 한 일
- 일정표(간트 차트) 작성과 작업 순서 결정
- 프론트 Vercel 배포 (대화 밖에서 진행)
- 설계 결정 (AI 질문에 대한 답)
  - 기준 멜로디: 음표 단위 — 이유: 삑사리를 음 하나씩 판정하려고
  - 음 높이: MIDI 번호 — 이유: 반음 차이 계산이 쉬움
  - 시간: 초 단위 — 이유: librosa 결과와 바로 비교 가능
  - 쉬는 구간: 음표 사이 공백 — 이유: 쉬는 구간은 채점하지 않음
  - 멜로디 위치: 프론트 `public`에 두고 서버는 `환경 변수 주소 + 곡 id`로 받음 (서버가 주소를 정함)
  - 곡 id: 허용 목록 — 이유: 곡이 적음
  - 장치: 노래/키보드 두 모드, 마이크 권한으로 판단. 권한은 버튼 클릭 때 요청 — 이유: 거절하면 다시 못 물음
  - 실패 처리: `NotReadableError`만 재시도 안내, 나머지와 예상 밖 에러는 키보드 모드
  - 업로드: multipart, 브라우저에서 wav 변환, 크기 3MB(48kHz 스테레오 + 여유로 직접 계산), 413/400 구분, `POST /audition/upload`, 응답은 곡 id와 길이
- 아이디어 제시: 늦게 시작하면 재시작 안내, 언제든 재시작 가능, 녹음 후 stream 종료와 재시작 때 권한 재확인
- 승인: stream은 타이머가 아니라 녹음 종료 즉시 닫기, 타이머는 최대 녹음 길이에만 사용

## C. AI 판단과 달리 사용자가 결정한 일
### C-1. 구현 방식
- AI 제안: 설계가 끝나면 사용자가 직접 구현하고 AI는 리뷰와 검증만 맡기 (멘토 지침 기준, 매 단계 "직접 구현해 보세요" 권장)
- 사용자 결정: 설계 결정은 직접 하고, 구현은 AI에 맡긴 뒤 리뷰로 역설계해 학습
- 결정 이유: 완성된 코드를 리뷰하며 역설계하는 쪽이 더 잘 배운다고 판단
- 결과: 검증 전 (리뷰 아직 안 함)

## 결과와 배운 점
- 결과: AI 서버 pytest 전체 통과(새 테스트 7개 포함). 로컬 브라우저에서 가짜 소리로 녹음 → wav → 업로드 → 200 응답(`duration: 1.92`), 400 안내, 마이크 닫힘, CORS 확인. 실제 마이크·Safari·배포 환경은 테스트 안 함. 커밋 안 함
- 배운 점: (나중에 작성)
- 다음 할 일: 코드 리뷰(역설계), librosa 음정 비교(11/25), 늦은 시작 처리(재시작 vs 시간 보정) 결정, 횟수 제한을 코스 추천과 따로 셀지 결정

# 썬그레이 오디션 MVP 2단계: 음정 분석 + LangGraph 심사

- 날짜: 2026-11-23
- 프로젝트: SceneWalk (Aleph Capstone) — SG 담당
- 사용 도구: Claude Code (Opus 5.5), librosa 1.0.1(pyin), LangGraph, OpenAI(gpt-4o-mini, 테스트에서는 꺼짐), pytest
- 목표: 녹음을 기준 멜로디와 음표별로 비교하고, 그 결과를 AI가 해석해 심사 피드백을 주게 한다.

## A. AI가 한 일
- 설계 검토와 반례: 늦은 시작은 녹음 지연(1.92초 사례)과 같은 문제, 시작 시각은 조건 충족 시점이 아니라 구간 시작이어야 함, "음~" 허밍은 길이 기준으로 못 막음
- 면접 관점 정리: 멜로디 임의 생성은 "AI를 왜 썼냐"의 답이 되지 않음(난수는 AI가 아님). 답은 "계산은 코드, 해석은 LLM, LLM 결과는 코드로 검사"
- 사실 확인: git 100MB 제한은 저장소 파일 단위라 라이브러리와 관계없음. 이 PC의 Windows 앱 제어 정책이 최신 scipy DLL을 막아 `scipy==1.16.3`으로 고정
- 구현 (사용자 위임, 세부 기준은 AI가 정함)
  - 음정 분석 `ai/app/audition_pitch.py`: pyin, 0.3초 voiced 구간으로 시간 보정, 옥타브 차이 무시, 정확 ±0.5반음, 삑사리 = 2반음 넘게 0.06초 이상 튐
  - LangGraph 심사 `ai/app/audition_judge.py`: 분석(코드) → 심사(LLM) → 검증(코드), 검증 실패 시 1번 재시도 후 규칙 문장으로 대체
  - 업로드 API 응답에 점수·음표별 판정·피드백 추가, 멜로디 못 받으면 503
  - 테스트 `ai/tests/test_audition_judge.py`: 사인파로 만든 가짜 노래로 검증
- 측정: 첫 요청 약 3초(numba 컴파일), 이후 약 0.3초

## B. 사용자가 직접 한 일
- 진행 순서 결정: 백엔드 핵심(분석·심사)이 없으면 화면보다 백엔드를 먼저 진행
- 설계 결정
  - 늦은 시작: 시간 보정 — 이유: 다시 부르게 하면 번거로움
  - 노래 시작 기준: voiced 프레임이 일정 시간 이상 이어질 때
  - 기준 시간 0.3초 — 이유: 가장 짧은 음표(0.5초)보다 짧아야 함
  - 노드 구성: 분석·심사·검증 3노드
- 문제 제기
  - 라이브러리 때문에 git 100MB 제한에 걸리지 않을지 확인
  - 멜로디 임의 생성 제안 — 이유: 여러 번 해도 지루하지 않게, "정적인데 AI 프레임워크를 왜 썼냐"는 질문에 답하기 위해
- 판단 수정: 처음에는 if문으로 어려운 부분을 "음정 정확도"라고 봤으나, 계산으로 되는 일이라는 반례를 검토한 뒤 "여러 음에 걸친 패턴 해석과 개선 조언"으로 수정
- 승인: 멜로디 임의 생성 대신 심사 해석을 AI의 역할로 두는 구조

## C. AI 판단과 달리 사용자가 결정한 일
- 없음 (구현 위임은 1단계 C-1과 같은 결정을 이어감)

## 결과와 배운 점
- 결과: AI 서버 테스트 61개 통과(새 테스트 14개). 브라우저에서 0.5초 늦게, 4번 음을 반음 낮게 부른 가짜 노래 → 92점, 보정 0.46초, 4번만 "낮음". 실제 LLM 호출·실제 목소리·배포 서버는 테스트 안 함. 커밋 안 함
- 배운 점: (나중에 작성)
- 다음 할 일: 실제 목소리로 임계값 조정, 실제 LLM으로 검증 노드 확인, 배포 서버에서 librosa 메모리·빌드 확인, 프론트 `uploadTake` 주석과 결과 화면을 새 응답에 맞추기

# 썬그레이 오디션 MVP 3단계: 오디션 세트 + 결과 화면

- 날짜: 2026-11-23
- 프로젝트: SceneWalk (Aleph Capstone) — SG 담당
- 사용 도구: Claude Code (Opus 5.5), React Three Fiber, Web Audio API, 브라우저 미리보기
- 목표: 게임 안에서 오디션 세트에 들어가 노래하고, 심사 결과를 화면으로 받게 한다.

## A. AI가 한 일
- 기존 구조 파악: 응원봉 게임(3D 감지·E키·패널) 방식, 뮤비 골목 좌표, 캐릭터 GLB의 Sit 동작
- 문제 제기: 부르는 동안 스피커로 멜로디를 틀면 마이크가 그 소리를 녹음해 채점이 틀어짐 → "미리 듣기 + 부르는 동안에는 화면 음표만"으로 진행 (사용자 답이 없어 AI 추천안 적용)
- 구현 (사용자 위임)
  - `sg_kpop.json`: 뮤비 골목 6채 → 4채, 골목 끝에 오디션 세트·벽, 입구 간판·게이트 추가
  - `sg_audition.jsx`: 입구 간판, 네온 게이트(전구 깜빡임·서치라이트), 오디션 세트(LED 벽·조명·마이크·카메라), 심사위원 3명(기존 캐릭터 GLB를 Sit 자세로 재사용), 마이크 앞 감지·E키
  - `AuditionPanel.jsx`: 미리 듣기 → 마이크 권한 → 3·2·1 → 녹음(음표 막대) → 심사 → 결과(점수·음표별 색·심사평), 시도 번호로 늦게 온 이전 결과 무시
  - 공용 파일: `App.jsx` 2줄, `styles/index.js` 2줄
- 검증 방법: 게임에 순간이동이 없어 `hub.json` 시작 위치를 검증 중에만 바꾸고 되돌림. 브라우저 마이크 함수를 가짜 노래로 바꿔 전체 흐름 확인
- 임의로 정한 것: 80점 이상 합격, 심사평은 특정 심사위원 이름 없이 표시, 키보드 모드는 "준비 중" 안내

## B. 사용자가 직접 한 일
- 오디션 위치 결정: 뮤비 촬영 골목을 축소해 구역 입구 쪽에 배치
- 연출 방향: 입구에서부터 보이게 화려하게
- 심사위원 구성: 프로듀서, 보컬 트레이너, 안무가 3명
- 모델링 방식: 필요하면 다른 AI 도구(Codex)로 모델을 만들어 넣어도 된다고 허용
- 2단계 PR: 처음 만든 PR이 `SG` 브랜치라 변경 0개인 것을 AI가 알린 뒤, 사용자가 `sg-audition` 브랜치로 PR을 다시 만들어 병합 — 증거: LimByungKwan/Aleph_Capstone#62
- 승인: AI가 제안한 골목 축소 방식(남길 건물 4채, 골목 끝 세트), 멜로디 안내 방식

## C. AI 판단과 달리 사용자가 결정한 일
### C-1. 오디션 위치
- AI 제안: SUNGRAY 엔터 건물 입구 (기획사 오디션이라는 설정과 가장 잘 맞음, 추천으로 표시)

- 사용자 결정: 로컬 `SG`는 두고 `sg-audition` 이름 사용
- 결정 이유: (미기록)

## 결과와 배운 점
- 결과: 게임 안에서 입구 게이트·세트·심사위원 표시, E키 → 미리 듣기 → 3·2·1 → 녹음 → 심사 → 결과(가짜 노래로 92점, 4번 음만 "낮음") 확인. 마이크 거절 시 키보드 모드 안내 확인. 프론트 빌드 성공. 실제 마이크·진짜 목소리·휴대폰 화면은 테스트 안 함. 커밋 안 함
- 배운 점: (나중에 작성)

# K-POP 돔 + 바닥선 서치라이트 + 밤 폭죽 + 올려다보기 카메라 (멀티 에이전트)

- 날짜: 2026-11-23
- 프로젝트: SceneWalk (Aleph Capstone) — SG 담당
- 사용 도구: Claude Code (Opus 5.5), Codex CLI (gpt-6-astra 추론 high: 구현, gpt-6-luna: 검토), React Three Fiber
- 목표: 잠실 올림픽 주경기장처럼 K-POP 구역을 감싸는 돔과 밤 공연 연출을 만든다.

## A. AI가 한 일
- Claude: 작업 분할과 계약 설계 — 돔 바닥선(둥근 사각형, 구역 좌표 x -44~40.5, z -44~46, 높이 18m)을 `sg_domeShape.js` 한 곳에 정의해 Codex와 Claude가 같은 선을 쓰게 함. 동쪽 광장 나무까지 여유 2m, 남쪽 해변을 조사해 범위 결정. 자체 검사(2m 간격 162점, 입구 제외 156점)
