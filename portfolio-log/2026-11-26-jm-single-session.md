# 2026-11-26 · 계정당 로그인 1곳 (새 로그인 우선)

- 날짜: 2026-11-26
- 프로젝트: SceneWalk AI (캡스톤)
- 도구: Supabase Auth(JWT) · PostgreSQL 함수/RLS, Node.js 22 + Express 5, ws 8, React, PGlite(로컬 SQL 검증), Claude Code
- 목표: 같은 계정으로 여러 기기에서 동시에 로그인하지 못하게 한다. 무료 플랜(Supabase "세션 1개" 설정 없음)과 `service_role` 키 없는 설계 안에서, 서버를 건너뛰는 요청까지 막는다.

## A. AI가 한 일
- 현재 구조 점검: 중복 로그인으로 데이터가 깨지는 경로가 있는지 먼저 확인 — 스탬프는 `UNIQUE(user_id, place_id)`, 쿠폰 사용은 `used_at is null` 조건부 갱신 + 멱등성 키라 동시 요청에도 한 번만 반영됨 (증거: `supabase/migrations/20261118120000_jm_core.sql` `redeem_coupon`)
- 정책 비교와 설계 — 증거: `supabase/migrations/20261130120000_jm_single_session.sql` 머리 주석
  - "기존 로그인 우선"은 훔친 쪽이 먼저 들어오면 진짜 사용자가 잠김 → **"새 로그인 우선"** 선택
  - 구분 기준: Supabase JWT의 `session_id` 클레임 (로그인 1번마다 새로 생기고 refresh해도 그대로). 라이브러리 타입 정의에서 필수 클레임인 것 확인
  - 계정마다 "지금 유효한 session_id" 1개만 `user_sessions`에 기록 (RLS 켜고 정책 없음 = 함수 전용)
- **두 겹**으로 막음
  - ① 서버 `requireAuth`가 매 요청 `session_ok()` → 아니면 401 `SESSION_REPLACED` (증거: `server/src/app.js`)
  - ② DB `require_user`(쓰기 함수 첫 줄)에 같은 검사 → 끊긴 기기가 공개 키 + 옛 토큰으로 Supabase를 **직접** 불러도 쓰기 거절
- 설계 중 찾아 고친 구멍 2개
  - 로그아웃 때 기록 행을 지우면 "기록 없음 = 통과" 규칙 때문에 앞서 끊긴 옛 토큰(훔친 것일 수 있음)이 되살아남 → 지우지 않고 `session_id = null`(어떤 토큰도 무효)로 바꿈. SQL 테스트 6번이 이 경우를 확인
  - 같은 브라우저의 탭들은 localStorage를 같이 써서, 끊긴 탭이 다른 탭의 새 로그인까지 지울 수 있음 → 저장된 토큰이 끊긴 그 토큰일 때만 지움 (증거: `frontend/src/api/session.js` `handleSessionReplaced`, `frontend/tests/session.test.mjs`)
- 감지·기록: 다른 기기를 끊으면 감사 로그 `session_replaced` (세션 id는 앞 8자리만). 로그아웃 뒤 다시 로그인은 "끊음"으로 남기지 않음
- 멀티 접속(WebSocket)도 계정당 1개: 끊긴 토큰은 4001로 거절, 같은 계정 새 연결이 오면 이전 연결 4002, 로그인 API가 다른 기기를 끊는 순간 그 계정 소켓도 바로 4001 (증거: `server/src/realtime.js` `closeUser`·`kickUser`, `server/src/index.js`). 화면은 4002면 다시 붙지 않음 → 두 탭이 서로 끊는 반복 방지
- 배포 순서 안전성: migration만 먼저 적용해도 기록이 없으면 모두 통과 → 순서는 migration → 서버 → 화면
- 테스트
  - SQL: `supabase/tests/jm_single_session_test.sql` 15개 + 기존 6파일 전부 다시 통과 (PGlite, 총 PASS 101개)
  - 서버: 10개 추가, 전체 98개 통과 (확인 실패 시 통과시키지 않고 500, 역할 검사보다 먼저 401, 로그아웃은 항상 204 등)
  - 화면: 3개 추가 (SESSION_REPLACED면 refresh 없이 로그아웃, 그냥 만료는 예전처럼 refresh)
- 팀원 파일은 고치지 않음: 병관님 서버 테스트의 가짜 Supabase에 `rpc`가 없어 처음에 실패 → 테스트를 고치지 않고, 멀티 접속에서 "세션 확인 자체가 실패하면 막지 않는다(API가 막음)" 규칙을 코드로 분명히 함

## B. 사용자가 직접 한 일
- 문제 제기: "계정 중복 로그인되는데 막아야 할까?"
- 최종 결정: 막는다. 방향(사장님 공용 계정 포함 예외 없이 + 시연 운영 규칙)을 승인

## C. AI 판단과 달리 사용자가 결정한 일
- AI는 처음에 **막지 않는 쪽**을 권했다: 데이터 경쟁은 DB가 이미 막고 있고, 공용 사장님 계정과 충돌하며, 토큰 도난에는 짧은 만료·refresh 회전·"모든 기기 로그아웃"이 더 직접적이라는 이유. 지민이 "보안에 문제가 되기 쉽다"며 막기로 결정 → 공용 계정 충돌은 "시연 때 사장님 화면은 한 사람만"이라는 운영 규칙으로 풀고, 시연 뒤 사장님 계정을 사람마다 1개씩 만드는 것으로 정리

## 결과와 배운 점
- 결과: 계정당 로그인 1곳, 서버 + DB 두 겹, 감사 로그 + 화면 안내까지. 로컬 검증 완료, 실제 DB·Render·Vercel 배포와 두 브라우저 실측은 배포 뒤
- 남는 한계(문서화): 끊긴 토큰으로 Supabase를 직접 부르면 "본인 데이터 읽기"는 만료(1시간) 전까지 가능. Auth 세션 자체를 끊으려면 `service_role` 키가 필요한데, 키 유출 피해가 더 커서 넣지 않음
- 배운 점: "막는다"보다 **어디서 강제하느냐**가 중요하다. 서버에서만 막으면 공개 키 + 토큰으로 DB를 직접 부르는 길이 남는다. 그리고 해제(로그아웃) 경로가 오히려 구멍을 다시 여는 경우가 있어서, 정상 흐름뿐 아니라 "끊긴 쪽이 되살아나는가"를 테스트로 확인해야 한다
- 면접 답 준비: "MySQL·자체 세션이라면 sessions 테이블에 세션 id를 두고 로그인 때 교체, 미들웨어에서 비교. 같은 원리를 Supabase JWT의 session_id로 구현했고, DB 함수에서 한 번 더 검사해서 서버 우회까지 막았다"

# 같은 날 추가 · 관리자 2단계 인증(TOTP) — "등록한 관리자만"

- 목표: 관리자 계정에 비밀번호 + 인증 앱 6자리를 걸되, 제출(11/30)·시연(12/01) 직전에 관리자 화면이 갑자기 막히지 않게 한다.

## A. AI가 한 일
- 방식 제안: 관리자 전원 강제 대신 **등록한 사람만** 요구 (전원 강제는 4명 모두 앱 설치·등록이 끝나야 하고, 한 명이라도 못 하면 시연이 막힘). 시연 뒤 전원 강제로 바꾸기 쉬운 구조(한 줄 삭제)로 둠 — 증거: `supabase/migrations/20261201120000_jm_admin_mfa.sql`
- 판정 기준: Supabase 토큰의 `aal`(비밀번호만 aal1, 코드까지 aal2) + `auth.mfa_factors`의 검증 완료 여부
- **두 겹**
  - ① 서버 `requireRole('admin')`이 403 `MFA_REQUIRED` (화면이 코드 창을 띄움) — 증거: `server/src/app.js` `mfaInfo`
  - ② DB `my_role()` 한 곳만 바꿔서, 그 함수를 쓰는 정책·함수 11곳(관리자 통계·감사 로그 읽기·남의 프로필 읽기·역할 변경 가드)에 한 번에 적용
- 서버는 `service_role` 키 없이 사용자 토큰으로 Supabase Auth REST(`/factors`, `/challenge`, `/verify`)를 부름 (supabase-js의 `auth.mfa`는 저장된 세션이 필요해서 서버에 맞지 않음 — 라이브러리 소스로 엔드포인트 확인) — 증거: `server/src/supabase.js` `authRest`
- 방어: 코드 형식(6자리)을 먼저 검사해 인증 서버를 부르지 않음, 계정별 15분 5번 실패 제한, 로그인 확인에 쓸 factor는 화면이 보낸 id가 아니라 서버가 찾음, 인증 서버 오류 내용(비밀·QR)은 로그에도 남기지 않음, 코드 확인 뒤 새 토큰도 계정당 로그인 1곳 기록에 반영
- 화면: 이름표 🔐(등록: QR + 직접 입력값 + 6자리), 로그인 뒤 코드 창(닫으면 순례객 기능만, 관리자 기능을 누르면 다시 뜸) — 증거: `frontend/src/components/auth/LoginPage.jsx`
- 테스트: SQL 8개(전체 8파일 통과), 서버 11개(전체 109), 화면 4개. 테스트 중 "역할 변경은 에러가 아니라 RLS 0행으로 조용히 막힌다"는 걸 발견해 검증 방식을 실제 동작에 맞춤
- 덤: 스탬프 진행률 테스트가 장소 수를 17로 고정해 팀원이 장소를 추가할 때마다 깨지던 것을 데이터에서 세도록 고침

## 결과와 배운 점
- 결과: 로컬 검증 완료. 실제 등록·로그인 실측은 배포 뒤 관리자 휴대폰이 필요
- 배운 점: 권한 판정을 함수 하나(`my_role`)에 모아 두면, 새 조건(2단계 인증)을 넣을 때 정책을 하나하나 고치지 않아도 된다. 반대로 그 함수가 바뀌면 영향 범위가 넓으므로, 기존 SQL 검증 7파일을 전부 다시 돌려 회귀를 확인했다
