# 3D 맵 걷는 중 끊김 원인 분석과 해결 (셰이더 재컴파일)

- 날짜: 2026-11-18
- 프로젝트: SceneWalk AI (4인 팀 캡스톤, 웹 3D 관광 맵) — SG 담당: 성능 최적화
- 사용 도구: Claude Code (Opus 5.5), Chrome DevTools Performance, React Three Fiber 9 / three.js 0.187, Vite, Python(트레이스 분석 스크립트)
- 목표: 캐릭터로 걸어 다닐 때 화면이 0.1~1초씩 멈추는 문제를 측정으로 원인을 찾아 해결한다.

## A. AI가 한 일
- 팀원 작업과 겹치는지 확인: 최신 main을 받아 SG 담당 파일 변경 여부와 겹치는 작업을 정리함(다른 팀원의 전체 맵 FPS 최적화, 사장님용 가게 통계) — 증거: `git diff` 결과(대화 기록)
- 첫 측정과 잘못된 추정: 앱 내장 브라우저에서 draw call(그리기 명령) 317개, 메시 4,224개, 재질 3,164개, `gl.render()` CPU 8.7ms를 재고 "CPU가 원인"이라고 추정함. 이후 사용자의 Chrome 녹화로 틀린 추정임이 드러남 — 증거: 대화 기록
- 트레이스 분석: 사용자가 녹화한 Chrome 트레이스(약 31초)를 Python으로 분석함. 평소 프레임은 60fps였고, 50ms 넘는 멈춤 13번(합계 3.9초) 동안 JS 샘플의 92%가 `getProgramInfoLog`(셰이더 컴파일 완료 대기)였음 — 증거: `Trace-20261118T104510.json.gz`
- 원인 확정 실험: 셰이더 캐시 키를 비교해 점광원 개수 칸만 `3`과 `11`로 다른 것을 확인함. 거리 숨김(`MapLayout.jsx`)이 조명 묶음을 숨기면 켜진 점광원 수가 바뀌고, three.js가 모든 재질 셰이더를 다시 컴파일한다는 것을 밝힘. 점광원을 임시로 고정하자 새 컴파일 11개 → 0개, 가장 느린 프레임 1,310ms → 27ms — 증거: 브라우저 측정 출력(대화 기록)
- 코드 작성(사용자가 맡김): `ShaderWarmup.jsx`(시작할 때 `compileAsync`로 미리 컴파일), `PointLightLock.jsx`(점광원을 항상 보이는 위치로 옮겨 개수 고정), `Scene.jsx` 4줄 추가 — 증거: 커밋 `e5fa29c`
- 나무 위치 수정(사용자가 맡김): `sg_backstage_tree1`이 무대 범위(남북 -11~11m) 안 z 8에 있어서 z 13으로 옮김 — 증거: `sg_kpop.json:78`, 커밋 `e5fa29c`
- 최신 main 반영: `git stash` → `git merge --ff-only` → `git stash pop`. 겹치는 줄 없음 확인, 빌드 통과
- 커밋과 푸시(사용자가 맡김): SG 브랜치에 커밋 `e5fa29c`를 푸시함

## B. 사용자가 직접 한 일
- 문제 발견: 실제 PC(Intel 내장 그래픽) Chrome에서 INP(입력 후 화면 반영까지 걸린 시간) 1.6초를 확인하고 문제를 제기함 — 증거: DevTools 스크린샷
- 측정 데이터 확보: Chrome Performance 녹화를 세 번(수정 전, 미리 컴파일 후, 조명 고정 후) 직접 해서 수정 전후 비교 근거를 만듦. AI 내장 브라우저는 30fps 제한이 있어 재현이 불가능했기 때문에, 사용자의 녹화가 원인을 확정한 결정적 데이터였음 — 증거: `Trace-20261118T104510.json.gz`, `Trace-20261118T110518_v2.json`, `Trace-20261118T111324_v3.json`
- 병합 충돌 예방 규칙: 남은 SG 작업은 새 파일로 만들고, 공용 파일은 불러오는 한두 줄만 고치는 규칙을 정함. 실제로 이번 수정은 새 파일 2개와 `Scene.jsx` 4줄로 끝남 — 증거: 프로젝트 지침 "병합 충돌 피하기"
- 설계 질문: "공용 셰이더로 통일하면 어떤가"를 제안해 검토함. three.js가 이미 같은 설정의 재질끼리 셰이더를 공유한다(3,164개 재질 → 38개 프로그램)는 설명을 듣고 보류함
- 검수: 수정본을 로컬에서 직접 걸어 보며 끊김 개선을 확인하고, 무대 앞으로 튀어나온 나무를 발견함 — 증거: 스크린샷
- 승인: 미리 컴파일 방식(`compileAsync`) 채택
- 승인: 최신 main을 받을 때 새로 clone하지 않고 기존 폴더에서 fast-forward(앞으로 감기)로 반영한 AI 방식

## C. AI 판단과 달리 사용자가 결정한 일
### C-1. 조명 개수 고정을 어디서 할지
- AI 제안: 정석은 다른 팀원 파일인 `MapLayout.jsx`에서 조명을 숨김 대상에서 빼는 것. 다른 팀원 파일이므로 팀에 먼저 말하는 쪽을 우선 추천함
- 사용자 결정: 팀에 묻기 전에, SG 새 파일(`PointLightLock.jsx`)로 우회한 버전을 로컬에서 먼저 만들어 직접 검수하기로 함
- 결정 이유: "일단 내가 검수하고 팀원한테 의견 전달할게" — 효과를 직접 확인한 근거를 들고 팀에 제안하려고 함
- 결과: 50ms 넘는 멈춤 13번 → 0번, 가장 긴 프레임 계산 1,057ms → 12ms. 다른 팀원 파일은 건드리지 않음. 우회 방식의 한계(조명을 항상 계산함, 원래 위치에서 분리됨)는 코드에 `shortcut:` 주석으로 남김

## 결과와 배운 점
- 결과 (사용자 PC Chrome 녹화, 각 31~34초)

| 항목 | 수정 전 | 미리 컴파일 후 | 조명 개수 고정 후 |
|---|---|---|---|
| 50ms 넘는 멈춤 | 13번, 3.9초 | 12번, 2.9초 | 0번 |
| 가장 긴 프레임 계산 | 1,057ms | 545ms | 12ms |
| 평소 프레임 계산 (중앙값) | 5.2ms | 4.8ms | 5.0ms |

  - 조건 차이: 수정 전은 빌드 버전, 나머지는 개발 서버로 측정함. 걸은 경로도 매번 다름
- 배운 점
  - "느리다"의 원인은 평균 성능이 아니라 가끔 생기는 긴 멈춤일 수 있다. 평균 FPS보다 가장 긴 프레임을 봐야 한다.
  - AI의 첫 추정(CPU 원인)은 틀렸다. 실제 환경에서 잰 트레이스가 추정을 바로잡았다.
  - three.js는 켜진 조명 개수를 셰이더에 박아 넣는다. 그래서 조명을 숨기는 최적화가 오히려 큰 멈춤을 만들 수 있다.
